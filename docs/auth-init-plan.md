# 认证初始化计划

## 1. 目标

本阶段目标是不新开业务大分支之前，先明确 `r-admin` 的认证初始化方案，为后续登录、当前用户信息、路由鉴权、动态菜单和 RBAC 权限链路提供统一入口。

当前项目已经具备：

1. 后端最小服务骨架
2. PostgreSQL 表结构与种子数据
3. 前端后台布局与原型页面
4. 前后端基础 CI 与 Docker 联调能力

因此下一步最合理的动作，不是继续扩展原型页，而是先建立认证主链路。

## 2. 为什么先做认证

认证初始化应当优先于用户、角色、权限 CRUD 页面，原因如下：

1. 没有登录链路，前端控制台只能停留在静态原型阶段
2. 没有当前用户上下文，后续动态菜单无法真实接入
3. 没有 Token 与鉴权中间件，后端权限控制无法形成闭环
4. 后续按钮权限、菜单权限、接口权限都依赖认证身份

一句话总结：

`先打通“谁登录、拿到什么身份、能访问什么”的主链路，再进入 RBAC 业务模块开发。`

## 3. 认证初始化范围

本阶段建议只覆盖最小认证闭环，不一次性引入全部安全增强能力。

建议纳入本阶段：

1. 账号密码登录
2. JWT Access Token 签发
3. 当前登录用户信息接口
4. 前端登录页
5. Token 本地存储
6. Axios 请求头自动附带 Token
7. 前端路由登录态守卫
8. 未登录跳转登录页
9. 退出登录

建议暂不纳入本阶段：

1. 图形验证码
2. Refresh Token
3. 记住我
4. 密码过期提醒
5. 账号锁定与失败次数限制
6. 单点登录
7. 多租户登录入口
8. 双因素认证

## 4. 后端建议落点

建议在 `backend/` 中新增认证模块，例如：

```text
backend/src/modules/auth/
├─ dto.rs
├─ handler.rs
├─ service.rs
└─ mod.rs
```

同时逐步补充以下基础能力：

1. `common/error.rs`
2. `common/jwt.rs`
3. `middleware/auth.rs`
4. `modules/user/` 或最小用户查询服务

后端本阶段最小职责：

1. 校验用户名和密码
2. 查询用户状态
3. 查询用户角色与权限基础信息
4. 生成 JWT
5. 解析 JWT
6. 将登录用户挂到请求上下文

## 5. 前端建议落点

建议在 `frontend/` 中新增：

```text
frontend/src/views/auth/
├─ LoginView.vue

frontend/src/stores/
├─ auth.ts

frontend/src/utils/
├─ auth.ts
```

前端本阶段最小职责：

1. 提供登录页表单
2. 调用登录接口
3. 保存 Access Token
4. 保存当前用户基础信息
5. 路由进入前校验登录态
6. 退出时清空登录态并跳转登录页

## 6. 建议接口设计

建议优先定义以下接口：

### 6.1 登录接口

```text
POST /api/auth/login
```

请求体建议：

```json
{
  "username": "admin",
  "password": "123456"
}
```

响应体建议：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "access_token": "jwt-token",
    "token_type": "Bearer",
    "expires_in": 7200,
    "user": {
      "id": 1,
      "username": "admin",
      "nickname": "超级管理员",
      "is_super_admin": true
    }
  }
}
```

### 6.2 当前用户信息接口

```text
GET /api/auth/me
```

建议返回：

1. 用户基础资料
2. 角色列表
3. 权限标识列表
4. 后续动态菜单所需的菜单树或菜单查询入口

### 6.3 退出接口

第一阶段可先只做前端本地退出：

```text
POST /api/auth/logout
```

如果暂时不做服务端 Token 失效，也可以先保留接口占位。

## 7. Token 策略建议

第一阶段建议采用最简单可靠的方案：

1. 只启用 Access Token
2. Token 放在前端本地存储
3. Axios 请求自动追加 `Authorization: Bearer <token>`
4. 后端中间件统一解析与校验

JWT Claims 最小建议包含：

1. `sub`：用户 ID
2. `username`
3. `exp`
4. `iat`
5. `is_super_admin`

后续再扩展：

1. `tenant_id`
2. `role_codes`
3. `token_version`

## 8. 路由与页面策略建议

前端建议新增公开路由：

1. `/login`

受保护路由：

1. `/dashboard`
2. `/system`
3. 后续所有后台页面

建议路由守卫规则：

1. 未登录访问受保护页面，跳转 `/login`
2. 已登录访问 `/login`，跳转 `/dashboard`
3. Token 存在但用户信息为空时，优先调用 `/api/auth/me`

## 9. 与 RBAC 的衔接方式

认证初始化阶段只需要把 RBAC 所需的最小用户身份信息准备好，不要求一次性做完整动态权限控制。

建议第一阶段先做到：

1. 登录成功后返回用户基础信息
2. 返回角色编码列表
3. 返回权限标识列表

后续第二阶段再接：

1. 动态菜单树
2. 路由按权限注册
3. 按钮级权限指令
4. 后端接口级权限校验

## 10. 推荐实现顺序

建议按下面顺序推进：

1. 后端补充认证配置项
2. 后端新增登录 DTO、登录接口与 JWT 工具
3. 后端新增 `/api/auth/me`
4. 前端新增登录页
5. 前端新增 `auth store`
6. 前端新增 Token 存储工具与 Axios 注入
7. 前端新增登录态路由守卫
8. 前后端联调登录与当前用户信息
9. 最后再开始动态菜单和用户/角色页面

## 11. 完成标准

当以下条件满足时，可认为认证初始化阶段完成：

1. 存在登录页
2. 可以通过账号密码登录
3. 登录成功后可进入控制台
4. 刷新页面后登录态可恢复
5. 未登录访问控制台会被拦截
6. 后端能校验 JWT
7. `/api/auth/me` 可正常返回当前用户基础信息

## 12. 后续衔接建议

认证初始化完成后，最自然的下一步是：

1. 动态菜单初始化
2. 当前用户信息接入到顶栏
3. 用户管理页
4. 角色管理页
5. 权限点管理页

一句话总结：

`认证初始化不是终点，而是 RBAC 主链路真正开始的起点。`
