# `/api/auth/menus` 接口设计

## 1. 目标

本文档用于定义 `r-admin` 动态菜单初始化阶段的后端接口契约，作为前后端后续对接 `/api/auth/menus` 的统一基线。

本接口的核心职责不是返回“所有系统菜单”，而是返回：

`当前登录用户在当前上下文下可见的菜单树`

也就是说，这个接口天然应该已经包含：

1. 当前用户身份过滤
2. 角色权限过滤
3. 菜单状态过滤
4. 菜单排序

## 2. 推荐接口定义

```text
GET /api/auth/menus
```

鉴权方式：

1. 需要携带 `Authorization: Bearer <token>`
2. 后端基于当前登录用户身份返回可见菜单

## 3. 为什么单独拆接口

当前项目已有：

```text
GET /api/auth/me
```

但菜单建议不要继续塞进 `/me`，原因如下：

1. `/me` 更适合承载“当前用户资料”
2. 菜单树天然比用户资料更复杂，独立维护更清晰
3. 后续菜单可能会受租户、组织、状态等影响
4. 后续如需单独刷新菜单，独立接口更灵活

一句话原则：

`/me` 负责“我是谁”，`/menus` 负责“我能看到什么导航结构”。`

## 4. 推荐响应结构

建议响应体保持与当前项目统一风格：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "menus": [
      {
        "id": "workspace",
        "name": "workspace",
        "title": "工作台",
        "icon": "histogram",
        "children": [
          {
            "id": "dashboard",
            "name": "dashboard",
            "title": "概览看板",
            "path": "/dashboard",
            "icon": "histogram"
          }
        ]
      }
    ]
  }
}
```

## 5. 菜单节点字段建议

建议一个菜单节点至少包含：

```json
{
  "id": "users",
  "name": "users",
  "title": "用户管理",
  "path": "/users",
  "icon": "user",
  "permission": "system:user:list",
  "hidden": false,
  "children": []
}
```

字段说明：

1. `id`
   菜单唯一标识，前后端都可以用它做稳定引用
2. `name`
   菜单内部名称，建议与前端路由名或业务标识保持一致
3. `title`
   菜单展示文案
4. `path`
   菜单跳转路径
5. `icon`
   前端图标映射名，不建议直接传前端组件名
6. `permission`
   当前菜单绑定的权限标识，可为空
7. `hidden`
   是否在侧边栏隐藏
8. `children`
   子菜单数组

## 6. 字段设计原则

### 6.1 `icon`

建议传字符串，不建议传组件名或 SVG 内容。

例如：

```json
"icon": "user"
```

原因：

1. 前后端边界更清晰
2. 前端可以统一做 icon map
3. 更利于后续多端复用

### 6.2 `path`

建议由后端返回最终可跳转路径。

例如：

```json
"path": "/system/users"
```

原因：

1. 前端不需要再自行拼装路径
2. 菜单配置和路由映射关系更清楚

### 6.3 `permission`

即便后端已经做完菜单过滤，也建议保留这个字段。

原因：

1. 前端调试时更容易定位菜单来源
2. 后续按钮权限、页面权限可以共用同一权限编码体系
3. 方便前端做二次校验或灰度展示

### 6.4 `children`

无子菜单时建议返回空数组 `[]`，不要返回 `null`。

原因：

1. 前端渲染更简单
2. 类型更稳定

## 7. 当前阶段推荐层级

当前阶段建议先支持两级菜单：

1. 一级分组
2. 二级可点击菜单项

例如：

```json
{
  "id": "access",
  "name": "access",
  "title": "权限管理",
  "children": [
    {
      "id": "users",
      "name": "users",
      "title": "用户管理",
      "path": "/users",
      "icon": "user",
      "permission": "system:user:list",
      "children": []
    }
  ]
}
```

当前不建议一上来就做无限层级菜单，原因是：

1. 当前项目页面还不多
2. 两级足够支撑第一版后台结构
3. 可以降低前后端联调复杂度

## 8. 后端过滤规则建议

后端建议在返回前完成以下过滤：

1. 菜单状态为启用
2. 菜单未逻辑删除
3. 当前用户有访问权限
4. 父级菜单若无可见子节点则不返回
5. 菜单按排序字段升序返回

这样前端拿到的 `menus` 可以直接用于渲染，而不必承担太多业务判断。

## 9. 推荐数据库映射关系

后续实现时，菜单返回一般会关联：

1. `sys_menu`
2. `sys_role_menu`
3. `sys_user_role`
4. `sys_role`

建议逻辑可以概括为：

`当前用户 -> 当前角色 -> 角色关联菜单 -> 构建树 -> 返回可见菜单`

如果超级管理员需要看全部菜单，也建议在服务层显式处理，不要让前端猜测。

## 10. 前端接入建议

当前前端已经预留：

1. [menu.ts](/D:/r-admin/frontend/src/api/menu.ts)
2. [menu.ts](/D:/r-admin/frontend/src/services/menu.ts)
3. [menu.ts](/D:/r-admin/frontend/src/stores/menu.ts)

当前策略是：

1. 优先请求 `/api/auth/menus`
2. 若接口尚未实现，则 fallback 到本地 mock 菜单

因此后端后续只要按本文档实现成功，前端就可以自然切换到真实接口。

## 11. 推荐错误语义

建议错误语义与现有认证接口保持一致：

1. 未登录或 token 无效：`401`
2. 账号禁用或无权访问：`403`
3. 服务内部异常：`500`

当前不建议对“无菜单”返回错误。

更合理的做法是：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "menus": []
  }
}
```

这样前端可以自然展示空菜单状态。

## 12. 推荐后续扩展字段

如果后续菜单体系要继续增强，可以逐步补充：

1. `type`
   例如：`directory` / `menu` / `external`
2. `sort`
   菜单排序值
3. `external_url`
   外链地址
4. `cacheable`
   页面是否建议缓存
5. `affix`
   是否固定到标签导航

但这些字段不建议在当前第一版一口气引入。

## 13. 第一版完成标准

当下面条件满足时，可认为 `/api/auth/menus` 第一版契约已经足够落地：

1. 返回结构固定为 `data.menus`
2. 菜单节点包含 `id / name / title / path / icon / permission / hidden / children`
3. `children` 稳定返回数组
4. 菜单已经完成权限过滤与排序
5. 超级管理员与普通角色的返回结果可明显区分

一句话总结：

`菜单接口的目标，不是把所有菜单定义都暴露给前端，而是把“当前用户实际可见的导航树”稳定返回出来。`
