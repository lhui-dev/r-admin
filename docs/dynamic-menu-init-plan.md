# 动态菜单初始化方案

## 1. 目标

本阶段目标是在 `feature/init-dynamic-menu` 分支上完成前端菜单初始化能力，让当前后台布局从“静态写死菜单”过渡到“可承接后端返回的菜单树”。

这一阶段不追求一次性做完完整权限系统，而是先打通下面这条链路：

`登录成功 -> 获取当前用户 -> 初始化菜单 -> 侧边栏按菜单树渲染`

## 2. 当前现状

当前项目已经具备：

1. 登录页与前端认证主链路
2. `/api/auth/me` 当前用户恢复能力
3. 顶栏用户信息接入
4. 侧边栏布局样式已稳定
5. 个人信息页和系统设置页等基础页面入口

当前问题在于：

1. [AppLayout.vue](../frontend/src/layouts/AppLayout.vue) 中的侧边栏菜单仍是本地静态数组
2. 顶部导航和侧边栏尚未从统一菜单源读取
3. 后续用户、角色、菜单管理页面无法基于真实菜单状态推进
4. 当前菜单与权限之间还没有形成清晰的数据关系

一句话总结：

`现在已经有了登录态，但登录后“应该看到什么菜单”还没有进入真实初始化阶段。`

## 3. 本阶段边界

本阶段建议纳入：

1. 定义前端菜单数据结构
2. 增加菜单 store
3. 增加菜单初始化入口
4. 让侧边栏从 store 渲染
5. 使用本地 mock 菜单树完成第一版联调形态
6. 为后续后端菜单接口预留接入点

本阶段建议暂不纳入：

1. 路由按权限动态注册
2. 按钮级权限指令
3. 菜单 CRUD 页面
4. 多租户切换联动菜单
5. 完整面包屑、标签页导航体系

一句话原则：

`先解决“菜单从哪里来、怎么渲染”，再解决“菜单怎么受权限精细控制”。`

## 4. 推荐数据来源

动态菜单有两种常见接法：

### 4.1 方案 A：由 `/api/auth/me` 扩展返回菜单树

优点：

1. 用户、角色、权限、菜单一次初始化完成
2. 前端应用启动时只需要一个核心 bootstrap 请求
3. 对早期项目最省接口设计成本

缺点：

1. `/me` 结构会越来越重
2. 后续如果菜单单独缓存或单独刷新，不够灵活

### 4.2 方案 B：新增独立菜单接口

例如：

```text
GET /api/auth/menus
```

优点：

1. 语义清晰
2. 菜单初始化可单独维护
3. 更适合后续菜单刷新、租户切换、权限联动扩展

缺点：

1. 启动阶段请求数会多一个
2. 前端初始化链路会稍复杂

### 4.3 当前阶段建议

当前更建议先按“前端本地 mock + 后续独立接口”来设计。

原因：

1. 当前后端 `/me` 已稳定，不建议在本阶段继续扩重
2. 菜单体系后续天然会比用户资料更复杂
3. 独立接口更符合后续 RBAC 演进方向

建议后续后端接口预留为：

```text
GET /api/auth/menus
```

接口字段建议与返回契约可参考：

[菜单接口设计](./auth-menus-api-design.md)

## 5. 前端菜单数据结构建议

建议前端先统一一份菜单节点结构：

```ts
type AppMenuItem = {
  id: string
  name: string
  title: string
  path?: string
  icon?: string
  permission?: string
  hidden?: boolean
  children?: AppMenuItem[]
}
```

字段说明：

1. `id`
   菜单唯一标识
2. `name`
   路由名或菜单内部标识
3. `title`
   展示标题
4. `path`
   点击跳转路径
5. `icon`
   图标名称，前端再做图标映射
6. `permission`
   与权限点的绑定标识，后续可用于裁剪显示
7. `hidden`
   是否在菜单中隐藏
8. `children`
   子菜单

## 7. Store 设计建议

建议新增：

```text
frontend/src/stores/menu.ts
```

建议最小职责：

1. 保存菜单树
2. 提供菜单初始化方法
3. 提供可见菜单列表
4. 提供根据路由匹配当前激活菜单的方法
5. 提供重置菜单的方法

建议最小状态：

```ts
const menuTree = ref<AppMenuItem[]>([])
const initialized = ref(false)
```

建议最小方法：

1. `initMenus()`
2. `setMenus()`
3. `resetMenus()`

## 8. 与 Auth 的衔接方式

当前认证链路中，最自然的菜单初始化时机有两个：

### 8.1 登录成功后初始化

流程：

1. 登录成功
2. 获取 `/me`
3. 初始化菜单
4. 进入控制台首页

优点：

1. 首次进入后台时菜单状态完整
2. 用户体验更自然

### 8.2 应用启动恢复时初始化

流程：

1. 本地 token 存在
2. `bootstrap()` 恢复当前用户
3. 初始化菜单
4. 再放行受保护路由

优点：

1. 刷新后菜单上下文也能恢复
2. 与现有认证恢复路径一致

### 8.3 当前阶段建议

建议菜单初始化与 `auth bootstrap` 保持同一时机触发。

原因：

1. 菜单本质上就是当前登录身份的展示结果
2. 这样最容易保证刷新后仍有菜单
3. 也最符合后续“权限变化重新初始化菜单”的演进方向

## 9. 布局改造建议

[AppLayout.vue](../frontend/src/layouts/AppLayout.vue) 当前有两份静态导航：

1. 顶部导航 `topNavItems`
2. 侧边栏导航 `sidebarSections`

本阶段建议：

1. 先只改造侧边栏，让它从菜单 store 读取
2. 顶部导航继续保留轻量静态入口
3. 等菜单体系稳定后，再决定顶部导航是否也来自统一菜单源

这样做的好处是：

1. 修改范围更小
2. 风险更低
3. 更符合“本阶段先把侧边菜单动态化”的目标

## 10. 路由策略建议

本阶段不建议立即做全量动态路由注册。

建议策略：

1. 页面路由仍先静态注册
2. 菜单只负责渲染与跳转
3. 后续真正需要“按权限裁剪路由”时再扩动态路由注册

原因：

1. 当前已有页面数量有限
2. 路由动态注册会显著增加复杂度
3. 静态路由 + 动态菜单展示更适合当前阶段

一句话理解：

`先动态菜单，后动态路由。`

## 11. 推荐实施顺序

建议按下面顺序推进：

1. 新增菜单类型定义
2. 新增本地 mock 菜单数据
3. 新增 `menu store`
4. 在登录恢复链路中接入菜单初始化
5. 改造 `AppLayout` 侧边栏读取 store
6. 为未开发菜单项补“建设中”提示
7. 最后补最小测试或联调验证

## 12. 完成标准

当下面条件满足时，可认为动态菜单初始化阶段第一版完成：

1. 侧边栏不再依赖页面内部静态数组
2. 菜单树由统一数据源驱动
3. 登录后可正常看到菜单
4. 刷新后菜单可恢复
5. 当前路由可正常高亮对应菜单
6. 未开发菜单项不会导致跳转报错
7. 已为后端独立菜单接口预留接入点

## 13. 下一阶段衔接

本阶段完成后，后续最自然的下一步是：

1. 接入真实菜单接口
2. 基于权限点裁剪菜单显示
3. 为用户管理、角色管理、菜单管理页面补真实路由
4. 再考虑动态路由注册与按钮权限控制

一句话总结：

`动态菜单初始化阶段的目标，不是把 RBAC 一次做完，而是让后台开始真正“按身份展示结构”。`
